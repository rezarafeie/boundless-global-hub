# Project architecture rules

- Enrollment SMS uses service-only per-course settings and enrollment/kind claims with the existing activation and lesson progress records; short SMS login hashes are consumed atomically into existing user sessions after rechecking payment, activation and course access, because reminders must not grant access or duplicate delivery.

- Course editing uses persistent section panels with compact scheduling disclosures; hidden panels remain mounted so navigation preserves unsaved course, message and gamification state without changing persistence or lifecycle rules.

- Hub API uses the contract-approved Supabase edge-function transport, constant-time shared-secret authentication, protected server-only identity mapping, access-scoped action adapters and existing academy lifecycle services; static hosting cannot implement production server routes.
- Hub authentication uses private HMAC OTP/ticket records and atomic service-only consumption; account.link accepts the shared-secret-verified X-Hub-User email as proof only when source_user_id equals the unique account.resolve match for that email, and identical repeats are idempotent; neither flow creates or merges accounts or matches by name, and an existing different binding is never replaced.
- Hub linking ignores phone-only duplicate rows only when they have no email, Hub binding or verified identity proof; email, bound-owner and proven-phone conflicts remain blocking, and duplicate history is never transferred.

- Rafiei Pay callbacks and reconciliation use the stored payment ID, provider-verified order identity and exact Toman amount; the saved enrollment is reread before success and reused for lifecycle notifications, so callback routing or outages cannot confirm another order or mark pending payments failed.

- Bot home menus use the common account actions for every role; a shared policy maps privileged reply-keyboard text to existing guarded callback handlers, and form listing requires explicit show_in_bot opt-in so web forms and direct links remain unaffected.

- Lead deduplication is non-destructive: mark repeated enrollments for lead-list exclusion and retain enrollment dependencies, because payments, access and CRM history must survive cleanup.
- Lead views share `uniqueCourseLeads` for person/course identity matching after access-scoped loading, because duplicate enrollment records must not inflate lead lists or expose other agents' data.
- Instagram enrollment automation uses server-only rule and event tables, verified admin sessions, and an authenticated durable webhook queue; enrollment and activation delegate to existing functions so access and notifications follow the website lifecycle.
- Sparse NovinHub form completions resolve page/form identity through the documented form-response API using exact response and person IDs, then verify the correlated conversation owner before sending; missing email is never fabricated.
- Long Instagram activation messages use the existing short bot deep link for the same activation token instead of the percent-encoded support prefill URL, preserving the support flow while fitting direct-message limits.
- NovinHub conversation replies send the documented JSON content payload; form-urlencoded replies returned provider errors during verified live delivery.
- Instagram activation followups reuse custom followup claims and logs, resolve recipients only from server-owned completed enrollment events, recheck conversation ownership and activation before sending, and never fall back to another channel; this preserves the existing lifecycle without identity guessing or duplicate bot delivery.
- Optional-email enrollment stays in create-enrollment, requires a server-only social credential and a server-verified free course, and skips missing-email lookups and recipient email delivery; ordinary website validation remains unchanged.
- Call center operations reuse the existing gateway and processing functions with server-validated roles and ownership; provider routing stays capture-only until its contract and staged rollout are verified.
- Call-center scheduled HTTP work requires a server-only credential, never a public API key or client body flag, because it can import private recordings and incur AI costs.
- Call transcripts keep the raw speech-to-text in raw_transcript; the saved transcript and speaker segments come from a length-guarded audio-aware AI correction, because corrections must never rewrite what was said.
- Telegram enrollment reports use a server-only numeric-chat ACL, private verified webhook updates and a service-only aggregate RPC; delegated readers cannot manage access or read student identities, report counts use enrollment creation time without the API row cap, and the persistent report button works without website-account linking while preserving the ordinary start flow.
- Dashboard course enrollment counts load every bounded, deterministically ordered page and use the same registration-record and half-open time-range definition as Telegram; only the latest successful request may display totals, so row caps, failed pages and stale period responses cannot masquerade as complete current counts. The numeric list and chronological chart share the same paginated records and interval; time bins include empty periods and sum to the list total. Compact reports omit zero-course detail and retain a zero-course summary without altering totals.
- Hub messenger actions reuse the existing messenger tables through service-only SQL access checks and an idempotent send ledger, because Hub must follow source membership rules and never get direct database or realtime access.
- Messenger↔Telegram sync relays through a DB insert trigger to an edge function that rereads the row by id, applies the shared recipient policy (private peer, support owner on staff replies, group mentions/replies only) plus hub_msg_can_access, and claims a unique out-link before sending; Telegram replies map back via the stored bot message id, so replays never duplicate and replies only reach chats the linked user can access.
