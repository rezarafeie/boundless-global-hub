# ورود با کاوه‌نگار برای سرویس‌های رفیعی‌هاب

این سند قرارداد پیشنهادی و امن برای افزودن «ورود با شماره موبایل و کد یک‌بارمصرف» به محصولات رفیعی‌هاب است. هر محصول می‌تواند این جریان را داخل بک‌اند خودش پیاده‌سازی کند و از حساب کاربری، نشست و قواعد دسترسی همان محصول استفاده کند.

> این سند راهنمای پیاده‌سازی است و به‌تنهایی به معنی وجود یک سرویس ورود مرکزی یا آماده‌بودن آن در همه محصولات نیست.

## ۱. تصویر کلی

کاوه‌نگار فقط مسئول تحویل کد از طریق پیامک یا تماس صوتی است. صحت کد، انقضا، تعداد تلاش‌ها، ساخت نشست و تشخیص کاربر باید در سرور محصول انجام شود.

```text
کاربر
  │ شماره موبایل
  ▼
فرانت‌اند محصول
  │ POST /auth/otp/send
  ▼
بک‌اند همان محصول ────────► Kavenegar Verify Lookup
  │                              │
  │ ذخیره امن چالش OTP            │ پیامک/تماس صوتی
  │                              ▼
  │                            کاربر
  │
  │ POST /auth/otp/verify
  │ بررسی اتمیک کد، انقضا و تلاش‌ها
  │ یافتن/ساختن کاربر و ساخت نشست
  ▼
نشست معتبر همان محصول
```

### مرز مسئولیت‌ها

| بخش | مسئولیت |
|---|---|
| کاوه‌نگار | ارسال کد با الگوی تأییدشده و برگرداندن نتیجه درخواست ارسال |
| بک‌اند محصول | تولید کد، ذخیره امن، محدودیت ارسال، تأیید، مصرف کد و ساخت نشست |
| فرانت‌اند | گرفتن شماره و کد، نمایش خطا و شمارش معکوس ارسال مجدد |
| رفیعی‌هاب | در صورت نیاز، انتقال کاربر به محصول؛ بدون دسترسی به کلید کاوه‌نگار یا کد OTP |

برای ورود OTP به وب‌هوک کاوه‌نگار نیاز نیست. تأیید کد با رکورد سرور انجام می‌شود، نه با پاسخ تحویل پیامک.

## ۲. پیش‌نیازهای پنل کاوه‌نگار

1. در پنل کاوه‌نگار یک `API Key` بسازید یا از کلید اختصاصی همان محصول استفاده کنید.
2. از بخش اعتبارسنجی، یک الگوی لاتین بسازید و منتظر تأیید آن بمانید.
3. در متن الگو حداقل از `%token` استفاده کنید؛ مثلاً:

```text
کد ورود شما به «نام محصول»: %token
این کد را در اختیار دیگران قرار ندهید.
```

4. نام الگو را بدون فاصله و مطابق نام تأییدشده در پنل تنظیم کنید؛ مثلاً `hublogin` یا نام اختصاصی محصول.
5. درخواست ارسال را به متد رسمی `Verify Lookup` بفرستید. این متد پارامترهای `receptor`، `template` و `token` را می‌پذیرد و پاسخ JSON دارد. [مستندات رسمی REST کاوه‌نگار](https://kavenegar.com/rest.html) و [معرفی سرویس اعتبارسنجی](https://kavenegar.com/sms/verification) مرجع این اتصال هستند.

### آدرس سرویس

```text
POST https://api.kavenegar.com/v1/{API_KEY}/verify/lookup.json
Content-Type: application/x-www-form-urlencoded

receptor=09123456789
template=hublogin
token=123456
type=sms
```

- `receptor`: شماره گیرنده؛ در نمونه این سند به شکل `09xxxxxxxxx` ارسال می‌شود.
- `template`: نام لاتین الگوی تأییدشده.
- `token`: کد تولیدشده در سرور.
- `type`: مقدار `sms` برای پیامک؛ در صورت فعال‌بودن و نیاز محصول می‌توان از امکان تماس صوتی الگو استفاده کرد.

کلید در مسیر URL قرار می‌گیرد؛ بنابراین نباید URL کامل، پاسخ حاوی کلید یا خطاهای حاوی آن در لاگ کلاینت، ابزار مانیتورینگ عمومی یا پیام خطای کاربر ثبت شود.

## ۳. تنظیمات محرمانه و محیطی

کلیدها فقط در Secret Manager بک‌اند یا Edge Function نگهداری شوند و هرگز وارد کد فرانت‌اند، مخزن Git یا پاسخ API نشوند.

| نام | الزام | توضیح |
|---|---|---|
| `KAVENEGAR_API_KEY` | اجباری | کلید صادرشده توسط کاوه‌نگار |
| `KAVENEGAR_OTP_TEMPLATE` | اجباری | نام الگوی تأییدشده؛ مثلاً `hublogin` |
| `OTP_HASH_SECRET` | اجباری | رمز مستقل و تصادفی برای HMAC کردن کدها |
| `OTP_TTL_SECONDS` | پیشنهادی | اعتبار کد؛ مقدار پیشنهادی `120` |
| `OTP_RESEND_SECONDS` | پیشنهادی | فاصله ارسال مجدد؛ مقدار پیشنهادی `60` |
| `OTP_MAX_ATTEMPTS` | پیشنهادی | حداکثر خطا برای هر چالش؛ مقدار پیشنهادی `5` |

کلید کاوه‌نگار و `OTP_HASH_SECRET` دو مقدار جدا هستند. از Service Role Key سوپابیس به‌عنوان رمز OTP استفاده نکنید.

## ۴. قرارداد API مشترک محصولات

مسیرها می‌توانند route بک‌اند محصول یا Supabase Edge Function باشند. نام‌های زیر قرارداد پیشنهادی هستند:

```text
POST /auth/otp/send
POST /auth/otp/verify
POST /auth/logout
```

در پیاده‌سازی با Edge Function، معادل پیشنهادی آن‌ها `send-otp`، `verify-otp` و `logout` است. فرانت‌اند با `supabase.functions.invoke()` یا URL کامل و publishable key درخواست می‌زند؛ هیچ Service Role Key در مرورگر قرار نمی‌گیرد.

### ۴.۱ ارسال کد

#### درخواست

```http
POST /auth/otp/send
Content-Type: application/json
```

```json
{
  "phone": "09123456789",
  "purpose": "login"
}
```

| فیلد | نوع | توضیح |
|---|---|---|
| `phone` | string | شماره موبایل با یکی از قالب‌های پشتیبانی‌شده |
| `purpose` | string | یکی از `login`، `register`، `phone_link` یا `password_reset` |

#### پاسخ موفق

```json
{
  "data": {
    "request_id": "7dc8d4eb-8a1d-4c6e-bf0a-ef5f1f8f2fc1",
    "expires_in": 120,
    "retry_after": 60,
    "destination": "0912***6789"
  }
}
```

قواعد:

- شماره قبل از هر جست‌وجو یا ذخیره‌سازی normalize شود.
- پاسخ موفق نباید وجود یا نبودن حساب را افشا کند.
- در صورت ارسال زودهنگام، `429` با `retry_after` برگردانده شود.
- کد، کلید یا شماره کامل در پاسخ و لاگ قرار نگیرد.
- قبول درخواست توسط کاوه‌نگار به معنی تحویل قطعی پیامک به گوشی نیست.

### ۴.۲ تأیید کد و ورود

#### درخواست

```json
{
  "request_id": "7dc8d4eb-8a1d-4c6e-bf0a-ef5f1f8f2fc1",
  "code": "123456"
}
```

#### پاسخ موفق

```json
{
  "data": {
    "session_token": "SERVER_GENERATED_SESSION",
    "user": {
      "id": "USER_ID_IN_THIS_APP",
      "phone": "+989123456789",
      "name": "نام کاربر"
    },
    "is_new_user": false
  }
}
```

`session_token` باید بعد از تأیید موفق و در سرور ساخته شود. اگر محصول از Supabase Auth استفاده می‌کند، نشست معتبر Supabase برگردانده شود؛ اگر سیستم نشست اختصاصی دارد، از سرویس موجود همان محصول استفاده کنید و مکانیزم دوم و موازی نسازید.

#### پاسخ نیازمند تکمیل پروفایل

اگر محصول برای کاربر جدید به نام یا اطلاعات دیگر نیاز دارد، می‌تواند به‌جای نشست نهایی یک توکن کوتاه‌مدت و تک‌منظوره بسازد:

```json
{
  "data": {
    "registration_token": "SHORT_LIVED_SINGLE_USE_TOKEN",
    "is_new_user": true
  }
}
```

این توکن فقط اجازه تکمیل ثبت‌نام همان شماره تأییدشده را دارد و نشست کامل محسوب نمی‌شود.

### ۴.۳ خروج

```http
POST /auth/logout
Authorization: Bearer USER_SESSION_TOKEN
```

```json
{
  "data": {
    "ok": true
  }
}
```

نشست باید در سرور باطل یا منقضی شود؛ حذف توکن از مرورگر به‌تنهایی کافی نیست.

## ۵. نرمال‌سازی شماره موبایل

قالب ذخیره‌سازی پیشنهادی در دیتابیس: `+989xxxxxxxxx`.

| ورودی کاربر | مقدار داخلی | مقدار نمونه برای `receptor` |
|---|---|---|
| `09123456789` | `+989123456789` | `09123456789` |
| `9123456789` | `+989123456789` | `09123456789` |
| `989123456789` | `+989123456789` | `09123456789` |
| `00989123456789` | `+989123456789` | `09123456789` |
| `+989123456789` | `+989123456789` | `09123456789` |

قبل از normalize، فاصله، خط تیره و ارقام فارسی/عربی به شکل کنترل‌شده تبدیل شوند. ورودی نامعتبر رد شود؛ اضافه‌کردن کورکشور به هر رشته‌ای قابل‌قبول نیست.

نکته مهم: تابع ارسال و تأیید باید از **یک تابع مشترک normalize** استفاده کنند. اگر یکی `09...` و دیگری `+989...` جست‌وجو کند، کد معتبر پیدا نمی‌شود.

## ۶. مدل داده پیشنهادی

برای محصولات جدید بهتر است هر ارسال یک چالش مستقل باشد؛ ذخیره فقط یک ردیف به‌ازای هر شماره، مدیریت هم‌زمانی و تلاش‌ها را دشوار می‌کند.

| ستون پیشنهادی | نوع | کاربرد |
|---|---|---|
| `id` | UUID | همان `request_id` عمومی |
| `phone` | text | شماره normalize‌شده |
| `purpose` | text | هدف چالش |
| `code_hash` | text | HMAC کد، نه خود کد |
| `expires_at` | timestamptz | انقضا در UTC |
| `attempts` | integer | تعداد تأییدهای ناموفق |
| `max_attempts` | integer | سقف تلاش |
| `last_sent_at` | timestamptz | کنترل ارسال مجدد |
| `consumed_at` | timestamptz nullable | مصرف یک‌باره کد |
| `provider_message_id` | text nullable | شناسه پیام کاوه‌نگار برای ردیابی |
| `created_at` | timestamptz | زمان ایجاد در UTC |

قواعد دسترسی:

- کلاینت ناشناس یا کاربر عادی نباید بتواند ردیف‌های OTP را بخواند یا تغییر دهد.
- خواندن و مصرف چالش فقط از بک‌اند با دسترسی سرویس انجام شود.
- RLS و Grantها مطابق نقش‌های واقعی همان محصول تنظیم شوند.
- زمان‌ها در UTC ذخیره شوند؛ تبدیل به Asia/Tehran فقط برای نمایش انجام شود.

## ۷. الگوریتم امن ارسال و تأیید

### ارسال

1. ورودی، `purpose` و شماره را اعتبارسنجی کنید.
2. محدودیت IP، شماره و دستگاه را بررسی کنید.
3. کد ۶ رقمی با `crypto.getRandomValues()` بسازید؛ از `Math.random()` استفاده نکنید.
4. کد را با HMAC-SHA256 و `OTP_HASH_SECRET` هش کنید.
5. چالش را با انقضا و شمارنده تلاش صفر ذخیره کنید.
6. با `Verify Lookup` درخواست ارسال بدهید.
7. هم HTTP status و هم `return.status === 200` را بررسی کنید.
8. در خطا، چالش را قابل‌استفاده نگه ندارید و پیام عمومی مناسب برگردانید.
9. فقط `request_id`، وضعیت و شناسه پیام را بدون داده حساس لاگ کنید.

### تأیید

1. `request_id` و قالب کد را اعتبارسنجی کنید.
2. چالش مصرف‌نشده و منقضی‌نشده را بخوانید.
3. در صورت عبور از `max_attempts`، چالش را مسدود کنید.
4. HMAC کد ورودی را با مقدار ذخیره‌شده به‌شکل constant-time مقایسه کنید.
5. کد اشتباه باید شمارنده تلاش را افزایش دهد.
6. کد درست باید با یک عملیات اتمیک مصرف شود تا دو درخواست هم‌زمان نتوانند دو نشست بسازند.
7. کاربر را با شماره تأییدشده پیدا یا طبق سیاست محصول بسازید.
8. نشست را در سرور بسازید و رویداد ورود را بدون کد و شماره کامل ثبت کنید.

### مصرف اتمیک

شرط مصرف باید در همان `UPDATE` یا RPC تراکنشی اعمال شود:

```text
id = request_id
AND consumed_at IS NULL
AND expires_at > now()
AND attempts < max_attempts
```

خواندن رکورد و سپس اجرای `UPDATE` جداگانه، بدون قفل یا شرط اتمیک، race condition ایجاد می‌کند.

## ۸. نمونه اتصال سرور به کاوه‌نگار

این نمونه فقط بخش تماس با سرویس است؛ تولید چالش، rate limit، هش و مصرف اتمیک باید مطابق بخش قبل در اطراف آن پیاده‌سازی شوند.

```ts
type KavenegarLookupResult = {
  return?: { status?: number; message?: string };
  entries?: Array<{ messageid?: number | string; status?: number }>;
};

export async function sendLoginOtp(input: {
  receptor: string; // 09xxxxxxxxx
  code: string;
}): Promise<{ providerMessageId: string | null }> {
  const apiKey = Deno.env.get("KAVENEGAR_API_KEY");
  const template = Deno.env.get("KAVENEGAR_OTP_TEMPLATE");

  if (!apiKey || !template) {
    throw new Error("OTP provider is not configured");
  }

  const endpoint = `https://api.kavenegar.com/v1/${apiKey}/verify/lookup.json`;
  const body = new URLSearchParams({
    receptor: input.receptor,
    template,
    token: input.code,
    type: "sms",
  });

  const response = await fetch(endpoint, {
    method: "POST",
    headers: { "Content-Type": "application/x-www-form-urlencoded" },
    body,
    signal: AbortSignal.timeout(10_000),
  });

  const result = await response.json().catch(() => null) as
    | KavenegarLookupResult
    | null;

  if (!response.ok || result?.return?.status !== 200) {
    // endpoint و response خام را لاگ نکنید؛ ممکن است داده حساس لو برود.
    throw new Error("OTP_PROVIDER_REJECTED");
  }

  const messageId = result.entries?.[0]?.messageid;
  return { providerMessageId: messageId == null ? null : String(messageId) };
}
```

## ۹. نمونه استفاده در فرانت‌اند

```ts
const sendResult = await supabase.functions.invoke("send-otp", {
  body: { phone, purpose: "login" },
});

if (sendResult.error || !sendResult.data?.data?.request_id) {
  throw new Error("ارسال کد انجام نشد؛ لطفاً دوباره تلاش کنید.");
}

const requestId = sendResult.data.data.request_id;

const verifyResult = await supabase.functions.invoke("verify-otp", {
  body: { request_id: requestId, code },
});

if (verifyResult.error || !verifyResult.data?.data?.session_token) {
  throw new Error("کد واردشده معتبر نیست یا منقضی شده است.");
}

// نشست را فقط با سرویس احراز هویت موجود محصول ذخیره و استفاده کنید.
```

در UI:

- تا پایان `retry_after` دکمه ارسال مجدد غیرفعال باشد.
- با کامل‌شدن طول کد، ارسال خودکار اختیاری است؛ باید از ارسال چندباره جلوگیری شود.
- بعد از خطای شبکه، وضعیت ورود «موفق» نمایش داده نشود.
- کد در URL، localStorage، analytics یا console قرار نگیرد.

## ۱۰. اتصال به حساب‌های موجود رفیعی‌هاب

- شماره تأییدشده معتبرترین مدرک مالکیت شماره در این جریان است.
- ابتدا حساب همان محصول با شماره normalize‌شده پیدا شود.
- اگر حساب با همان ایمیل اما شماره دیگر وجود دارد، بدون تأیید مالکیت، حساب‌ها ادغام نشوند.
- اگر شماره قبلاً به حساب دیگری متصل است، ساخت حساب تکراری انجام نشود.
- تداخل ایمیل یا شماره باید `409 ACCOUNT_CONFLICT` بدهد و برای ادغام، جریان تأیید جداگانه لازم باشد.
- `hub_user_id` یا شناسه داخلی محصول نباید از ورودی کاربر ساخته یا تغییر داده شود.
- تأیید OTP به‌تنهایی نباید نقش ادمین، دسترسی مالی یا مالکیت داده دیگری اعطا کند.

اگر هاب قرار باشد نشست مشترک بسازد، باید قرارداد جداگانه‌ای برای تبادل توکن، اعتبارسنجی، انقضا و خروج تعریف شود. ارسال `session_token` یک محصول به محصول دیگر به‌عنوان نشست قابل‌قبول، بدون چنین قراردادی مجاز نیست.

## ۱۱. محدودیت ارسال و مقاوم در برابر سوءاستفاده

مقادیر زیر نقطه شروع پیشنهادی‌اند و باید با رفتار واقعی کاربران تنظیم شوند:

| محدودیت | مقدار پیشنهادی |
|---|---|
| فاصله دو پیام برای یک شماره | ۶۰ ثانیه |
| اعتبار هر کد | ۱۲۰ ثانیه |
| تلاش ناموفق برای هر چالش | ۵ بار |
| ارسال برای یک شماره | حداکثر ۵ بار در ساعت |
| ارسال از یک IP | محدودیت مستقل و قابل پیکربندی |

اقدامات تکمیلی:

- CAPTCHA یا چالش ضدربات بعد از الگوی مشکوک.
- عدم افشای اینکه شماره قبلاً ثبت‌نام کرده است یا نه.
- عدم تلاش مجدد خودکار و بی‌نهایت به کاوه‌نگار.
- عدم ساخت چند کد فعال بی‌نهایت برای یک شماره.
- ثبت متریک ارسال، خطا، تأیید و مسدودسازی بدون ذخیره کد.

## ۱۲. خطاهای قرارداد

| HTTP | کد پیشنهادی | پیام فارسی مناسب |
|---|---|---|
| `400` | `INVALID_PHONE` | شماره موبایل معتبر نیست. |
| `400` | `INVALID_CODE` | کد واردشده معتبر نیست. |
| `400` | `OTP_EXPIRED` | کد منقضی شده است؛ کد جدید دریافت کنید. |
| `400` | `OTP_ALREADY_USED` | این کد استفاده شده است؛ کد جدید دریافت کنید. |
| `409` | `ACCOUNT_CONFLICT` | این اطلاعات با حساب دیگری متصل است. |
| `429` | `OTP_RESEND_TOO_SOON` | برای ارسال دوباره کد کمی صبر کنید. |
| `429` | `OTP_ATTEMPTS_EXCEEDED` | تعداد تلاش‌ها بیش از حد مجاز است؛ کد جدید دریافت کنید. |
| `502` | `OTP_PROVIDER_ERROR` | ارسال پیامک انجام نشد؛ لطفاً دوباره تلاش کنید. |
| `500` | `SESSION_CREATION_FAILED` | ورود تکمیل نشد؛ لطفاً دوباره تلاش کنید. |

پاسخ خطا نباید متن خام کاوه‌نگار، API Key، کوئری دیتابیس یا stack trace را افشا کند.

## ۱۳. سازگاری با پیاده‌سازی فعلی آکادمی

پیاده‌سازی فعلی آکادمی از Edge Functionهای `send-otp` و `verify-otp` و الگوی `academylogin` استفاده می‌کند. کد فعلی ۴ رقمی است و ۵ دقیقه اعتبار دارد. جدول فعلی `otp_verifications` است و تأیید با شماره normalize‌شده انجام می‌شود.

این قرارداد برای استفاده در سرویس‌های دیگر هاب، چند تفاوت امنیتی مهم دارد که باید هنگام استفاده مجدد لحاظ شود:

| وضعیت فعلی آکادمی | قرارداد پیشنهادی برای محصولات هاب |
|---|---|
| کد ۴ رقمی و ۵ دقیقه اعتبار | کد ۶ رقمی و اعتبار کوتاه‌تر، طبق سیاست محصول |
| ذخیره خود کد | ذخیره HMAC کد |
| ساخت کد با `Math.random()` | تولید با CSPRNG مرورگرِ سرور، یعنی Web Crypto |
| تأیید کد و ساخت نشست در دو مرحله جدا | تأیید و ساخت نشست در بک‌اند |
| یک ردیف به‌ازای شناسه | چالش مستقل با `request_id` |
| بدون قرارداد عمومی برای تلاش و ارسال مجدد | سقف تلاش، rate limit و مصرف اتمیک |

همچنین کلید کاوه‌نگار نباید از ثابت داخل سورس کپی شود و لاگ کد، شماره کامل یا URL حاوی کلید نباید به محصولات دیگر منتقل شود. این موارد بدهی امنیتی پیاده‌سازی فعلی‌اند، نه الگوی قابل‌استفاده مجدد.

برای حفظ سازگاری موقت در همان آکادمی می‌توان ورودی قدیمی `{ phone, otpCode }` را کنار قرارداد جدید نگه داشت؛ اما برای محصولات جدید بهتر است از همان ابتدا `request_id` و ساخت نشست سمت سرور استفاده شود.

## ۱۴. تست پذیرش قبل از انتشار

### کاوه‌نگار

- [ ] الگو تأییدشده و نام آن دقیقاً با Secret محیط یکسان است.
- [ ] ارسال واقعی به یک شماره آزمایشی انجام و دریافت پیام مشاهده شده است.
- [ ] هم خطای HTTP و هم `return.status` غیر ۲۰۰ به‌درستی خطا تلقی می‌شوند.
- [ ] کلید در فرانت‌اند، bundle، لاگ و پاسخ API دیده نمی‌شود.

### صحت جریان

- [ ] شماره‌های `09...`, `9...`, `98...`, `0098...` و `+98...` یک نتیجه normalize می‌دهند.
- [ ] کد درست، نشست همان کاربر را می‌سازد.
- [ ] کد اشتباه نشست نمی‌سازد و شمارنده تلاش را افزایش می‌دهد.
- [ ] کد منقضی و کد مصرف‌شده رد می‌شوند.
- [ ] دو تأیید هم‌زمان با یک کد، دو ورود موفق ایجاد نمی‌کنند.
- [ ] ارسال مجدد زودهنگام `429` می‌دهد.
- [ ] کاربر جدید فقط طبق سیاست همان محصول ساخته می‌شود.
- [ ] حساب با ایمیل یا شماره متداخل بدون تأیید ادغام نمی‌شود.
- [ ] خروج، نشست را در سرور باطل می‌کند.

### امنیت و پایداری

- [ ] کد و `OTP_HASH_SECRET` در دیتابیس یا لاگ به شکل قابل‌خواندن ذخیره نمی‌شوند.
- [ ] خواندن جدول OTP با anon یا کاربر عادی ممکن نیست.
- [ ] قطعی کاوه‌نگار باعث ورود بدون کد یا نمایش موفقیت کاذب نمی‌شود.
- [ ] خطای ساخت نشست بعد از تأیید کد، پیام موفقیت نمایش نمی‌دهد.
- [ ] هیچ retry خودکار بی‌نهایتی برای ارسال پیامک وجود ندارد.

## ۱۵. استقرار تدریجی

1. ابتدا در محیط آزمایشی با یک شماره واقعی و الگوی تأییدشده تست کنید.
2. ارسال و تأیید را با متریک و لاگ امن منتشر کنید.
3. ابتدا درصد کوچکی از کاربران را به ورود OTP هدایت کنید.
4. نرخ خطای ارسال، نرخ تأیید، زمان پاسخ و تعداد مسدودسازی را بررسی کنید.
5. ورود با رمز فعلی را تا پایدارشدن OTP حذف نکنید، مگر سیاست محصول چیز دیگری باشد.
6. بعد از انتشار کامل، تست دوره‌ای انقضا، مصرف یک‌باره، rate limit و خروج انجام شود.
